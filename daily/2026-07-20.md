# 2026-07-20

## Hermes / Hermes-adjacent

- No new tagged release today; `v0.18.2` (`v2026.7.7.2`) remains latest. Three genuine fixes landed on `main`:
  - **Gateway: two follow-up fixes to the delivery ledger, closing a "spend the redelivery budget without ever sending" bug.** Yesterday's durable delivery-obligation ledger (#67181) caps redelivery at `MAX_ATTEMPTS=3`, but `sweep_recoverable()` was incrementing `attempts` on every claim regardless of whether a platform adapter was actually connected. If the platform that owned a pending obligation failed to connect on this boot, `_redeliver_pending_obligations()` hit its "adapter is None" branch and skipped the send — but the attempt was already spent. Reproduced against the real runner: three boots with an unconnected adapter burned all three attempts with zero sends attempted, and the row was permanently `abandoned` on the fourth boot even though the underlying network issue (the same one that likely caused the crash) could recover later. The fix lets the caller declare which platforms it can actually send on this boot, so rows for unavailable platforms are left unclaimed instead of losing an attempt. A same-day companion fix (`gateway/run.py`) stops a related fast-redelivery loop on slow restarts. Direct correctness fix for the reliability feature shipped yesterday — without it, the ledger could still silently lose a message on a platform that's down at boot.
    https://github.com/NousResearch/hermes-agent/commit/371ee065fd
  - **Streaming: text-only stream drops with no `finish_reason` are now caught and retried.** When a provider stream ends cleanly (HTTP 200) after delivering partial text but no tool calls, and never sends a `finish_reason`, the chunk collector previously stamped `finish_reason='stop'` by default — silently presenting truncated text as a complete response. A third stream-drop path (alongside the existing zero-chunk and mid-tool-call cases) now routes text-only drops through the same partial-stream-stub machinery, so the conversation loop shows "Stream interrupted — requesting continuation" and gives the model a chance to resume. Observed in the wild with the DeepSeek provider, where CloudFront drops SSE streams mid-response. Direct correctness fix for anyone on providers/proxies that terminate SSE streams without a clean `finish_reason`.
    https://github.com/NousResearch/hermes-agent/commit/65bb16c8ce
  - **MCP: opt-out for automatic reload on config-change now lands in the right config section.** Yesterday's new `mcp.auto_reload_on_config_change` toggle (for users whose `config.yaml` mcp_servers section changes frequently and don't want each change to invalidate the provider prompt cache) was read from the wrong config path in its first commit; a fast follow-up moved it to read from `auxiliary.mcp` as intended, then a second same-day fix relocated it again to the top-level `mcp:` section with added regression tests. Minor but relevant for anyone tuning MCP reload behavior to protect prompt-cache costs.
    https://github.com/NousResearch/hermes-agent/commit/60092f728c
