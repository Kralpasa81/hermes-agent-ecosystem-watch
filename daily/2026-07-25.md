# 2026-07-25

## Hermes / Hermes-adjacent

- **Cross-session message leak fixed in the desktop app.** A queued background prompt (`fromQueue: true`) whose runtime binding had been reaped by the gateway fired with `sessionId=null`; the fallback expression then defaulted to whichever session the user was currently viewing, landing the queued message in the wrong session. The fix guards the fallback so a background drain only inherits the foreground session when it actually targets the current view — otherwise it stays `null` and rebinds correctly through the existing resume path. Real user-visible correctness bug: messages could appear in the wrong conversation.
  https://github.com/NousResearch/hermes-agent/commit/062d261955
- **Terminal tool stopped leaking `HERMES_SESSION_*` identity between concurrent sessions.** One long-lived backend serves many sessions (gateway, TUI, desktop/web) through a single shared bash environment. That environment cached a snapshot of `export -p`, which baked in the *first* session's `HERMES_SESSION_ID` — every later session sourcing the same snapshot then reported a foreign session's id, overriding the correct per-command env injection. Confirmed on staging with two concurrent sessions on one backend. Fix strips the per-session bridged vars from the snapshot at both write sites so identity is re-injected fresh per command instead of inherited from a neighbor.
  https://github.com/NousResearch/hermes-agent/commit/f2e32ceead
- **Crash-survivable in-flight turn journal ships for desktop.** Previously, a full app or machine crash mid-turn silently dropped everything the crashed turn had streamed — the renderer's session cache was memory-only and the backend's inflight snapshot died with the process. The visible tail (prompt + streamed assistant rows, tool calls included) is now journaled to `localStorage` (throttled, bounded to 24 entries / 7 days, cleared once the turn settles) and folded back onto the transcript on resume, merging with any live backend projection instead of treating it as already caught up.
  https://github.com/NousResearch/hermes-agent/commit/8d8d1d61fe
- **Gateway fix closes a silent first-message-loss bug on slow cold starts.** When the deferred agent build (MCP discovery with retry backoff, model-metadata fetch, skills scanning) outlived the hardcoded 30s wait, the old path emitted an error event and gave up without ever submitting the user's first prompt — it looked like a blank session with no visible error. The new waiter keeps the prompt attached to the running build and delivers it the moment the build finishes, shows one "still starting" notice past 30s, and only fails permanently if the build itself actually fails (bounded at 600s, configurable via `agent.build_wait_timeout`).
  https://github.com/NousResearch/hermes-agent/commit/60c8fc6290
- **`hermes update` no longer stalls for minutes on large `state.db` files.** The post-update integrity guard ran an unbounded `PRAGMA integrity_check`, whose cost scales with database size; measured at 143.5s on a real 30 GB `state.db` with zero visible output, looking like a hang right after "Code updated!". Fix bounds the check to 2 GiB by default (with a fast structural probe for oversized files) — same measured case dropped to 0.001s while corruption detection stayed intact for both zeroed-header and malformed-schema cases.
  https://github.com/NousResearch/hermes-agent/commit/01232e8e21
- **Two state-recovery data-loss paths closed.** A cross-process race let two writable startups clobber each other's quarantine of a zeroed `state.db`, erasing the original damaged-file evidence; now a cross-process lock with PID-suffixed, non-clobbering renames prevents it. Separately, an oversized `state.db` being skipped by the size cap (without being tracked as "failed") let automatic pruning delete the only other recoverable snapshot; oversized files are now tracked explicitly and pruning is suppressed whenever any failed/oversized DB exists.
  https://github.com/NousResearch/hermes-agent/commit/6048696ed0
- No new tagged release since **v0.19.0 "Quicksilver"** (Jul 20). Today's volume is unusually high post-release stabilization and correctness/reliability work, not a version bump.
